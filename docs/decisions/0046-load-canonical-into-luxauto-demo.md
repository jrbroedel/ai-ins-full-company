# ADR 0046 — Load the canonical book into luxauto_demo (Option B): DB as demo source of truth

Status: Accepted — 2026-08-30. STEP ONE of the demo-dashboard refresh (the new tiles are later steps).
Builds on ADR 0043/0045 (freeze-and-derive; the $71M artifact) and ADR 0031/0032/0030/0010/0035
(referral gate, override, quote creation, bind, state onboarding).

## Context
The demo dashboard should be powered by the DB (the project's true data source), showing the frozen
$71M canonical book (`sample-data/canonical/canonical_dataset.json`, sha256 `faa3c9b7…`) instead of
the accumulated synthetic junk currently in `luxauto_demo` (32,231 apps / 19,669 quotes / 0 policies).
So the frozen artifact must be loaded THROUGH the platform's own SECURITY DEFINER write paths, so the
audit trail (decision_log, policy_events) is generated by the platform, not hand-forged — while
preserving the artifact's per-month rate softening, which a re-rate would strip.

## Decision

1. **Rebuild, not mutate.** `decision_log` / `policy_events` / etc. carry append-only DELETE guards, so
   the old junk cannot be scoped-deleted. `scripts/load-canonical-to-demo.sh` does `DROP SCHEMA public
   CASCADE; CREATE SCHEMA public;` then re-applies `schemas/db/postgresql_schema.sql` via the normal
   `apply-and-verify-schema.sh` path. **Target guard is belt-and-braces and non-negotiable:** the
   wrapper forces `PGDATABASE=luxauto_demo` before sourcing creds, refuses `luxauto`, asserts the live
   `current_database()` is `luxauto_demo`, and the DROP runs inside a psql session that re-asserts the
   same in a DO block. Production `luxauto` is never dropped or written.

2. **Re-seed the rating world FROM the artifact's embedded `rating_snapshot`.** A fresh apply already
   seeds the 84 base rates, the 5 category→class mappings, `T0`, and `CT@1.1200` (via `onboard_state`).
   The loader onboards the other 49 states with their snapshot territory factors through the sanctioned
   `onboard_state()` path, then asserts full parity with the snapshot and that
   `compute_indicative_premium()` reproduces the artifact's `rating_basis` to the cent — so the DB
   rates are guaranteed identical to what produced the artifact's premiums.

3. **Hybrid load — functions everywhere except the one premium collision.**
   - EVERY submission: insert applicant/application/vehicle/claims/prior_insurance, then
     `submit_application()` → the REAL referral engine writes `decision_log`.
   - BOUND submissions only: **INSERT the quote row directly** carrying the artifact's SOFTENED
     `premium` + the DB rater's own breakdown as `rating_basis` (tagged with `softening_index` and
     `sold_premium`), then `bind_policy()` (reads premium off the quote, does NOT re-rate).
     `create_quote()` is NOT used: it re-rates via `compute_indicative_premium()` and would return the
     un-softened base ($82.1M book vs the frozen $71.3M), stripping the softening.
   - Refer/decline get `submit_application` only — no quote, no policy.
   - `submitted_at` is PRE-SET to the artifact's submission date so AL-01/VV-03's 5-year look-back is
     anchored to the frozen operating year, not load day (otherwise ~37 declines' claims fall outside
     the window and their `decision_log` reads AUTO_PROCEED — an incoherent "clean" audit on a
     declined risk).

4. **Frozen verdict carried in a dedicated table, not the engine, not `status`.** STEP 0 dry-run
   (70 submissions, Python replication validated 0/70 mismatches against the live engine, then the
   full 10,500 projected exactly) found the DB taxonomy CANNOT reproduce the artifact's
   bind/refer/decline mix:
   - **99.9% (7,648/7,655) of BIND submissions → AUTO_PROCEED** (clear the create_quote gate; `bind_policy`
     doesn't re-check it anyway). 7 trip AL-01's severe-single-claim limb → MANUAL_REVIEW_REQUIRED
     (bound regardless; a 0.09% audit-coherence note, not a blocker).
   - **refer AND decline both collapse into MANUAL_REVIEW_REQUIRED**, with leakage to AUTO_PROCEED
     (all 789 refer → 465 MANUAL_REVIEW / 324 AUTO_PROCEED; all 2,056 decline → MANUAL_REVIEW_REQUIRED).
     The engine has **no producer for DECLINE_RECOMMENDED** here (EL-01 needs sub-$100k values, which the
     book never has) and none for HARD_DECLINE (needs a sanctions hit).
   - Engine-native bind/refer/decline rollup ≈ **75.9 / 24.1 / 0.0** vs artifact **72.9 / 7.5 / 19.6** —
     material drift, refer inflated 3×, decline vanishes.

   Resolution (Dash decision at the STEP 0 gate): store each submission's frozen artifact disposition in
   `canonical_load_disposition (application_id → bind/refer/decline, engine_action)` — NOT
   `applications.status`, NOT `decision_log` (append-only, engine-owned). The engine still runs and
   writes its real `decision_log` (that drives reason codes and the referral view); the load-tag table
   is the authoritative OUTCOME alongside it, exactly as the artifact's premium is authoritative over a
   re-rate (ADR 0043 freeze-and-derive). The board's disposition mix and bind ratio are sourced from
   this table, never re-derived from the engine. **The engine action and the frozen outcome are BOTH
   true**: the engine routed the risk to review (it never auto-declines except sanctions), and in this
   frozen year review declined it — so the demo's ~20% declined is a modeled underwriting outcome, not
   an AI auto-decline. We do NOT add a decline rule to the engine and do NOT accept the raw engine mix.

5. **Policy-period claims in a demo-load table.** No DB table exists for the artifact's 453
   forward-looking claims (they were artifact-only; `claims_history` is PRIOR claims on applications).
   The loader creates `canonical_policy_period_claims`, joined to the bound policies by the unique
   `policy_number` (the artifact policy_id ≠ the DB-generated policy_id), so `Σ incurred / GWP == 0.5600`
   is computable off the DB.

6. **Bound-only quotes (approved hybrid), bind_ratio denominator fix deferred to the exporter step.**
   No indicative quotes for refer/decline (keeps the create_quote gate clean; avoids conflating the
   artifact's "what-it-would-have-cost" figure with an issued quote). Consequence:
   `quotes_issued == bound == 7,655`, so the current exporter's `bind_ratio = bound/quotes_issued` = 1.0.
   The fix — `bind_ratio = count(disposition='bind')/count(*)` sourced from `canonical_load_disposition`
   (= 7,655/10,500 = 0.729) — lands with the exporter/frontend step, along with sourcing
   `disposition_mix` from the same table and reading avg/GWP off `premium_amount` (the rating view's
   `indicative_premium` is the un-softened base). Not in this step's committed scope.

## Consequences
- Committed deliverable: `scripts/lib/load_canonical_to_demo.py` + `scripts/load-canonical-to-demo.sh`
  + this ADR. The DB state itself is not in git. Two new demo-load tables
  (`canonical_load_disposition`, `canonical_policy_period_claims`) are created by the loader, not the
  canonical schema (they are demo-load artifacts; `verify_schema.py` is unaffected by extra objects).
- Verified off the DB by direct SQL (authoritative): `luxauto_policy_view` count == 7,655;
  Σ bound `premium_amount` == $71,301,212.64; claims == 453; Σ incurred / GWP == 0.5600; frozen mix
  7,655 / 789 / 2,056. Softening preserved (Σ bound `premium_amount` $71.3M vs un-softened base $82.1M).
- Known exporter gaps for the next step (bind_ratio denominator, disposition_mix source, avg/GWP off
  `premium_amount`) are recorded above; the current exporter run reflects them until then.
- `program_id` on the loaded quotes is NULL and broker channel/rate are faithful defaults
  (wholesale / 12.5%); the commission waterfall (which needs a program panel) is a separate step.
