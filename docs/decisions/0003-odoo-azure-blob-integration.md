# ADR 0003: Odoo attachment storage on Azure Blob Storage — approach

**Status:** Researched, leaning decided — needs hands-on verification against a real Odoo instance before being treated as final.
**Date:** 2026-08-09
**Follows from:** ADR 0002, which flagged this as unscoped work.

## Recommendation

Use **OCA's `fs_storage` + `fs_attachment` modules** (from the actively-maintained [OCA/storage](https://github.com/OCA/storage) project), configured with the `abfs` protocol (Azure Blob Storage, via the `adlfs` Python package) for the underlying filesystem connection.

This is a lean, not yet a final decision - see "What still needs verification" below.

## Why: four options evaluated

### 1. Odoo's native "Cloud Storage" feature (built-in, supports Azure) — ruled out for our primary need
Recent Odoo versions ship a first-party Settings → Cloud Storage integration that supports both Google Cloud and Microsoft Azure. It looks like the obvious answer at first glance, but Odoo's own documentation states plainly: **"Files generated by Odoo (e.g., sales orders) and Documents/Sign app files are always stored on the database's server"** regardless of this setting - the feature only offloads chatter and email attachments. Our actual need (appraisals, loss runs, engineering reports, generated quote PDFs attached to Policy/Application records) is exactly the category this feature explicitly does not cover. Ruled out as a primary solution; it may still be worth enabling later as a secondary optimization for chatter/email specifically, but it doesn't solve the problem this ADR is about.

Also unconfirmed: whether this feature is available in Community edition or is Enterprise-only. Moot given the scope limitation above, but worth knowing if it's revisited as a secondary optimization.

### 2. `attachment_azure` (Odoo Apps Store) — ruled out, appears unmaintained
This module does what we actually need at first read — stores all attachments (documents and assets) on Azure Blob Storage via the `ir_attachment.location` system parameter, not just chatter. However, the listing found is versioned for **Odoo 9.0** - a version from roughly 2015-2016 - with no evidence of updates for current Odoo versions. Treat as effectively unmaintained rather than a live option, despite being the closest-sounding name to what we need.

### 3. OCA `fs_storage` + `fs_attachment` — recommended
This is the current-generation, actively maintained successor in the same OCA/storage project (available through at least the 19.0 branch, tracking current Odoo releases). Key differences from option 2 that make it the better fit:

- **Broader coverage, not chatter-limited.** It overrides Odoo's core `ir.attachment` storage hooks (`_file_read`/`_file_write`/`_file_delete`) directly, so it applies to *any* attachment - manually uploaded documents, attachments on custom models we build (a Policy or Application record's appraisal/loss-run/engineering-report files), and Odoo-generated report PDFs that get cached as attachments. This is the comprehensive behavior the native Cloud Storage feature explicitly lacks.
- **Protocol-agnostic via `fsspec`.** `fs_storage` doesn't hardcode a cloud provider - it exposes any protocol supported by the Python `fsspec` library. Azure Blob Storage is supported through **`adlfs`**, a mature, actively-maintained `fsspec` implementation (protocol `abfs`), not a one-off community plugin.
- **Free and open source**, consistent with the rest of this project's Odoo Community / self-hosted approach - no separate purchase, no vendor lock to a specific paid module's maintenance lifecycle.
- **Portable if the cloud provider decision ever changes.** Because the protocol is configuration (`abfs` today), not code, a hypothetical future move off Azure would be a configuration change in this module rather than a rewrite - useful given ADR 0002's standing (not technical) preference for Azure could in principle be revisited.

### 4. Custom build against `ir.attachment`'s override hooks — fallback only
Odoo's own `ir_attachment.py` documents exactly the extension points OCA's module uses (`_file_read`, `_file_write`, `_file_delete`, with support for custom location URI schemes). We could write this ourselves directly against Azure's `azure-storage-blob` SDK. Rejected as the primary path only because option 3 already does this well and is maintained by a large existing community - reinventing it would be pure risk with no compensating benefit. Worth falling back to only if hands-on testing of option 3 turns up a blocking problem specific to our setup.

## What still needs verification (this is why status is "leaning," not "decided")

- Confirm `fs_attachment`/`fs_storage` version compatibility with whatever specific Odoo version we deploy - **resolved by ADR 0004: Odoo 19.0**, which has an active `fs_attachment`/`fs_storage` branch in OCA's storage project.
- Actually stand up a `abfs`/`adlfs` connection against a real Azure Blob Storage account and confirm read/write/delete works end-to-end through Odoo, including for a custom model's attachment field (this project's real use case), not just chatter.
- Confirm license compatibility - OCA modules are typically AGPL-3, which should be compatible with Odoo Community's own AGPL-3 license, but worth a direct check rather than an assumption given how central this module becomes to the data layer.
- Decide whether the native Cloud Storage feature (option 1) is worth also enabling for chatter/email specifically, as a secondary, non-conflicting optimization - not required, purely optional.

## Consequences

- This becomes a real dependency our Odoo deployment carries (OCA/storage's `fs_storage` + `fs_attachment` + the `adlfs` Python package) - needs to be tracked alongside whatever quota-share custom module work happens (per ADR 0001).
- Document storage architecture is now: Azure Blob Storage as the physical store, `fs_attachment` as the Odoo-side integration layer, `abfs`/`adlfs` as the protocol bridge between them.
