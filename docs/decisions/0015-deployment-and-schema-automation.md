# ADR 0015: Deployment and schema automation

**Status:** Decided; not yet implemented (scripts are follow-on work)
**Date:** 2026-08-12
**Follows from:** ADR 0011 (named the schema-idempotency gap), ADR 0012 (named the VM-deploy gap), ADR 0014 (a second, independent instance of the same category of bug ADR 0011 first found)

## What this ADR decides

ADR 0011 and ADR 0012 each named a real process gap and explicitly declined to close it on the spot - deliberately, the same discipline this project applies to every gap it doesn't solve inline (endorsements in ADR 0010, the temporal-overlap gap in ADR 0007). Both gaps are the same shape of problem on two different layers: a step that's supposed to happen reliably has no standing mechanism confirming that it did. ADR 0014's implementation then found a *third* instance of it - the schema file's own internal ordering had never been checked against a genuinely fresh database - which is what makes closing this now rather than later worth doing: the same category of bug has now surfaced three times across three ADRs, each caught by hand, each time by a different person's (well, session's) diligence rather than anything structural. This ADR decides four things: how `postgresql_schema.sql` becomes safely re-runnable without turning into a migration framework, what a verify step checks and how it stays accurate as the schema grows, what the VM-side deploy script does, and where both live.

## 1. Idempotent re-apply: three mechanical patterns, not a migration framework

**Decision, one pattern per object type already in the file:**

- **Tables and indexes:** `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`. Both exclusion constraints in the file (`state_rating_table_versions`, `policy_endorsements`) are defined inline inside their `CREATE TABLE` statement, not as a separate `ALTER TABLE ... ADD CONSTRAINT` - so wrapping the table creation in `IF NOT EXISTS` handles them for free, no separate treatment needed.
- **Types (enums):** Postgres has no `CREATE TYPE IF NOT EXISTS`. Wrapped in `DO $$ BEGIN ... EXCEPTION WHEN duplicate_object THEN NULL; END $$;`.
- **Regular triggers:** `CREATE OR REPLACE TRIGGER` - native, idempotent syntax added in Postgres 14, confirmed working against `luxauto-pg`'s actual Postgres 16 in this session before writing this ADR. Covers 9 of the file's 10 triggers.
- **The one constraint trigger** (`program_participants_sum_check`, `CREATE CONSTRAINT TRIGGER`): `CREATE OR REPLACE TRIGGER` does **not** support the `CONSTRAINT` variant - tested live and confirmed rejected outright (`ERROR: CREATE OR REPLACE CONSTRAINT TRIGGER is not supported`). This one needs the same `DO $$ ... EXCEPTION WHEN duplicate_object` wrapping as enum types instead.
- **Functions and views:** `CREATE OR REPLACE` - already idempotent, unchanged. Worth noting explicitly: this was never the source of the ADR 0014 fresh-apply bug. That bug was about statement *ordering* (a function referencing a table that didn't exist yet), not idempotency - `CREATE OR REPLACE FUNCTION` has always safely re-run against an existing function. The two problems look similar (both make "just run the file again" unsafe) but have different causes and different fixes; this ADR's idempotency work doesn't touch or re-litigate the ordering fix ADR 0014 already made.
- **Extensions and grants:** already idempotent (`CREATE EXTENSION IF NOT EXISTS` was already in the file since ADR 0001/0002; re-granting an existing privilege is a Postgres no-op, not an error). No change needed.

**Explicitly not a migration-framework adoption.** This project has one living schema file, maintained as the current-state source of truth, extended in place by every ADR since ADR 0005 - not a sequence of versioned migration files applied incrementally (Flyway/Alembic/Rails-style). That practice continues unchanged. This decision only makes the one file safely re-runnable against a database that already has some or all of its objects - a narrower, purely mechanical problem than schema versioning. "Re-run the whole file" remains the actual deployment story; it just stops being destructive-by-omission (erroring out partway through, exactly as both ADR 0011's missing-schema discovery and ADR 0014's ordering bug independently demonstrated) when part or all of it is already there.

## 2. A verify step that stays accurate as the schema grows, not a hand-maintained checklist

**Decision: the same script that applies the schema also verifies it afterward, by parsing `postgresql_schema.sql` itself for every `CREATE TABLE`/`TYPE`/`FUNCTION`/`VIEW`/`TRIGGER` name, then querying `information_schema`/`pg_catalog` to confirm each one actually exists in the target database. Reports pass/fail per object. Exits non-zero if anything expected is missing.**

The reason the expected-object list is *parsed from the file* rather than hand-maintained as a separate list inside the verify script: a hand-maintained list is exactly the same failure mode this whole ADR exists to close - a second place someone has to remember to update, which will eventually drift the way ADR 0008's "loaded and verified" claim drifted from reality by ADR 0011. Deriving the expected list from the file that's already the single source of truth means the verify step can't fall behind the schema it's checking; every future ADR that adds a table, type, function, view, or trigger to `postgresql_schema.sql` is automatically covered by verification the next time this script runs, with nothing extra to remember.

This directly closes the specific gap ADR 0011 named: "a clean exit code assumed as proof" was exactly what let ADR 0008's claim stand unchecked for as long as it did (`psql -f` completing without error was treated as "loaded," when what was actually needed was confirmation the objects existed). The verify step makes the exit code mean what it's assumed to mean.

As of this ADR, that's 22 tables, 16 enum types, 12 function signatures (`calculate_premium_waterfall`'s two overloads count separately), 4 views, and 10 triggers (9 regular plus the one constraint trigger) - counted directly against the file line by line while writing this amendment, not written here as a list to keep in sync by hand, but as a snapshot confirming the scale of what the parse-and-verify approach needs to handle correctly, most importantly the overloaded function case (two entries sharing a name, distinguished by argument list, both need to independently verify present).

**Decision: before the parser is trusted to drive the verify step's pass/fail logic against a live database, its extracted counts must be cross-checked against this snapshot as the parser's own acceptance test.** The snapshot above isn't decoration - it's the expected output of a correct parser run against today's file, established by manually counting `CREATE` statements by category rather than trusting the parser to grade itself. If the parser's counts don't match it, that's a parser bug (a missed multi-line `CREATE TYPE`, a regex that double-counts the overloaded `calculate_premium_waterfall`, a trigger definition it fails to recognize) to fix before the parser goes anywhere near a live database - not a sign the schema itself has drifted, and not something to paper over by adjusting the baseline to match whatever the parser happened to produce. The baseline is fixed by the manual count; the parser is what has to prove itself against it, not the other way around.

## 3. The VM-side deploy script: safer than the manual practice it replaces, on purpose

**Decision: a second script, run on `luxauto-odoo`, that (1) checks for dirty local state in `/opt/odoo-custom-addons/luxauto` and fails loudly if any exists, rather than discarding it; (2) `git pull`s; (3) restarts the Odoo service; (4) runs a smoke test via the XML-RPC-as-disposable-user pattern already used by hand every deploy this project has done, confirming the models are actually queryable post-deploy - not just that the service came back up.**

Step (1) is a deliberate departure from how this has actually been done by hand in every session so far: when the VM's clone had leftover dirty state from manual pre-commit testing, the practical fix each time was `git checkout -- . && git clean -fd` to discard it before pulling - safe in that context because the operator (a session with full visibility into what it had just tested) could tell the difference between "my own known test-sync leftovers" and "someone's real uncommitted work." A script running unattended can't make that same judgment call - it has no way to know which case it's looking at - so the safe default is to refuse and surface the dirty state for a human to look at, not to guess. This makes the script *more conservative* than the manual practice it's replacing, deliberately: a good automated default and a good manual judgment call aren't always the same thing, and this is a case where they diverge.

Step (4) is what turns "the service is active" into an actual verification. `systemctl is-active odoo` (what every session so far has checked after a restart) confirms the process is running, not that it's serving correct data through a working registry - exactly the gap between "clean exit code" and "actually verified" that section 2 closes on the database side. The smoke test creates a disposable user in a minimal group, queries each of the four `luxauto.*` models via XML-RPC (the same real-authentication, real-ACL path used to catch the ADR 0010 `res.users` field-rename and the ADR 0013 search-view schema issue - both by hand, both things a superuser `odoo shell` check would have missed), and deletes the user afterward. If any model fails to load or read, the script exits non-zero instead of reporting success on a broken deploy.

Credential handling follows the pattern ADR 0009 already established rather than inventing a new one: secrets (Postgres admin credentials for the apply-and-verify script; whatever the VM-side script needs) are fetched via this VM's managed identity against Key Vault at run time, never stored in the script or passed through an operator's terminal history.

**Not decided here, and deliberately left open:** what triggers either script - manual invocation, a cron job, or real CI/CD. ADR 0012 already declined to pick a CI/CD tool under time pressure, and this ADR doesn't revisit that; it makes both scripts trustworthy to run, by hand or otherwise, without deciding who runs them or when.

## 4. Both scripts live in the repo, under `scripts/`

**Decision: a new top-level `scripts/` directory, sibling to `schemas/`, `odoo/`, `infra/`, `docs/` - `scripts/apply-and-verify-schema.sh` and `scripts/deploy-vm.sh`.** Versioned, reviewed, and rolled back the same as everything else in this repo - not VM-local shell history or a jump-box artifact, which is exactly the failure mode ADR 0008's original schema load fell into (a one-off operator action with no durable record). `apply-and-verify-schema.sh` is a thin wrapper around `psql` (connects, applies `schemas/db/postgresql_schema.sql`, runs the parse-and-verify pass); `deploy-vm.sh` is a bash script (git, `systemctl`, and a small Python XML-RPC smoke-test payload, the same shape as the ad hoc scripts already written and discarded by hand each session in `scratchpad/` - promoted here to a real, kept artifact instead of being rebuilt from scratch every time).

## Consequences

- Every future ADR that adds schema objects gets verification for free, with no separate list to update - the parse-from-file approach is the mechanism that makes that true, not a promise to remember.
- The manual `git checkout -- . && git clean -fd` pattern used by hand in every deploy so far is retired for the *automated* path; it remains a reasonable thing for a human operator to do deliberately when they know what they're discarding, but the script itself refuses and asks instead.
- Neither script decides *when* it runs - that's still open, consistent with ADR 0012's own explicit non-decision on CI/CD.
- `scripts/` becomes a new top-level convention in this repo, the same way `odoo/` did in ADR 0012 - worth keeping to as more automation gets built, rather than letting future scripts scatter into ad hoc locations.
- Not yet decided, left for the implementation task: the exact parsing approach for extracting object names from `postgresql_schema.sql` (regex over `CREATE ...` statements is the obvious first pass; whether that's robust enough or needs something sturdier is worth checking against the real file, not assumed here), and the precise Key Vault secret names/managed-identity scope the deploy script needs beyond what ADR 0009 already provisioned.
